# Deploy Echo

The deployment uses **Vercel** for the React frontend, **Render** for the Spring Boot API, and an externally managed **MySQL** database. The frontend is live at `https://echo-waste-management.vercel.app`; the API at `https://echo-waste-management.onrender.com` still needs a valid database connection before it can become healthy. The backend uses the `prod` profile, Flyway migrations, and an exact-origin CORS allow-list.

## 1. Push the project to GitHub

Create a private GitHub repository, then from the project root:

```powershell
git init
git add .
git commit -m "Prepare Echo for deployment"
git branch -M main
git remote add origin https://github.com/YOUR_ACCOUNT/echo-waste-management.git
git push -u origin main
```

Replace the remote URL with your repository. Never commit `.env` files, database passwords, or signing keys.

## 2. Create the production MySQL database

Create a private MySQL database on Render or another managed provider. Enable backups before storing real resident data. Use the credentials generated by the provider; do **not** use the local `echo_user` / `echo_password` values from `database/create-database.sql`.

Record the host, port, database name, user, and password for the backend environment variables.

## 3. Deploy the backend to Render

### Option A: Render Blueprint (recommended)

1. In Render, choose **New > Blueprint** and connect the GitHub repository.
2. Render detects `render.yaml` and creates the `echo-waste-backend` Docker web service from `backend/`.
3. Fill every variable marked `sync: false` in the Render dashboard before the first deploy completes.

### Option B: manual Render web service

1. Create a **Web Service** from the GitHub repository.
2. Set **Runtime** to `Docker`, **Root Directory** to `backend`, and **Dockerfile Path** to `Dockerfile`.
3. Set **Health Check Path** to `/api/health`.
4. Add the environment variables below.

Render injects `PORT`; the application already binds `server.port` to `${PORT:8081}`.

| Variable | Value |
|---|---|
| `SPRING_PROFILES_ACTIVE` | `prod` |
| `DB_URL` | `jdbc:mysql://<mysql-host>:<mysql-port>/<database>?serverTimezone=UTC` (add any SSL parameters required by the provider) |
| `DB_USER` | Database user from the provider |
| `DB_PASSWORD` | Database password from the provider |
| `JWT_SECRET` | Private random value of at least 32 characters (the Blueprint generates one) |
| `FRONTEND_URL` | `https://echo-waste-management.vercel.app` (replace if using a custom frontend domain) |
| `BOOTSTRAP_ADMIN_EMAIL` | Admin email for first startup only |
| `BOOTSTRAP_ADMIN_PASSWORD` | Strong unique password for first startup only |
| `BOOTSTRAP_ADMIN_NAME` | Admin display name |

On first startup, Flyway applies `V1__initial_schema.sql` and `V2__add_data_defaults_and_constraints.sql`, then the bootstrap admin is created only if that email does not exist. After the first successful deployment, remove the three `BOOTSTRAP_ADMIN_*` variables and redeploy; the account remains in MySQL. Never use the local demo accounts in production.

Check the Render deploy logs for successful Flyway migration and application startup. Then open:

```text
https://echo-waste-management.onrender.com/api/health
```

A healthy service returns:

```json
{"status":"ok","application":"echo-waste","database":"UP"}
```

A database failure returns HTTP 503 with `"status":"degraded"` and `"database":"DOWN"`.

## 4. Deploy the frontend to Vercel

1. Import the same GitHub repository into Vercel.
2. Set **Root Directory** to `frontend`.
3. Vercel should detect Vite; confirm:
   - **Build Command:** `npm run build`
   - **Output Directory:** `dist`
4. Add this build-time environment variable before deploying:

| Variable | Value |
|---|---|
| `VITE_API_URL` | `https://echo-waste-management.onrender.com/api` |

No API hostname is hardcoded in the frontend. If `VITE_API_URL` is missing, the built app falls back to same-origin `/api`, which is only suitable when the API is served from the same origin. The Render service must allow the exact Vercel origin in `FRONTEND_URL`; update it if you use a custom frontend domain, then redeploy the backend.

## 5. Verify the live deployment

1. Confirm `/api/health` returns `"database":"UP"`.
2. Open the Vercel URL and register a citizen account.
3. Sign in, submit a pickup request, and confirm it appears in the citizen calendar and request list.
4. Sign in with the bootstrap admin, approve the request, and assign the demo/collector account.
5. Sign in as the collector and move the assignment to `IN_PROGRESS` then `COLLECTED`.
6. Submit feedback and report a service issue; confirm the admin queues show both.
7. Confirm the new account, request, assignment, feedback, and issue rows exist in the production MySQL database.
8. Remove the bootstrap admin variables, redeploy, and confirm the admin can still sign in.
9. Set up a custom domain and HTTPS only after these checks pass.

## Production settings and limitations

- The `prod` profile requires `DB_URL`, `DB_USER`, `DB_PASSWORD`, `JWT_SECRET`, and `FRONTEND_URL`; startup fails if they are absent.
- `spring.jpa.hibernate.ddl-auto=validate` is used with Flyway. Add a new migration for every schema change; never edit an already-applied migration.
- Demo users and demo pickups are not seeded in production. Admin access uses the one-time bootstrap variables above.
- CORS accepts only the configured `FRONTEND_URL` in production; local Vite origins are allowed only in the default development profile.
- CI (`.github/workflows/build.yml`) runs `npm ci` / `npm run build` for the frontend and `mvn --batch-mode verify` for the backend.
- Before accepting real personal data, add a privacy notice and retention process, review account recovery and abuse controls, add rate limiting/audit logging, and rehearse database backup restoration.
